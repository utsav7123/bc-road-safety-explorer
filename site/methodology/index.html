Dashboard/Methodology

Methodology

Make the metric traceable from source to chart.

This project uses public aggregate road safety tables from RoadSafetyBC. The pipeline downloads the source CSV files, reshapes them into a consistent year-category-value format, validates numeric values, and generates a compact JSON dataset for the dashboard.

Data cleaning

The loader supports both wide government tables with one column per year and long tables with an explicit year field. Commas and simple suppression markers are removed before numeric conversion. Empty rows, invalid years, and non-numeric measures are excluded.

KPI design

Each KPI keeps a definition, source, refresh cadence, caveat, latest year, current value, and five-year change. This mirrors the idea that a performance measure should describe not only the numerator but how the number is meant to be interpreted.

Trend analysis

Annual series are sorted by year and summarized without smoothing so the original published values remain visible. The playable timeline highlights one observation at a time rather than replacing the source series.

Regional map

The map is a geospatial visualization of aggregate police traffic regions. Region coordinates are approximate visual anchors. They are not crash coordinates and should not be used for hotspot or intersection-level conclusions.

Forecasting

A linear regression is fit to the most recent ten annual fatality totals and projected three years forward. This is intentionally simple so the model can be explained. It does not estimate causal effects or replace an official forecast.

Known limitations

Police reporting practices and coverage have changed over time. Public aggregate tables also limit what can be learned about exposure, intersection-level risk, individual crash circumstances, and causal factors. The dashboard therefore focuses on descriptive monitoring and transparent baseline analysis.
